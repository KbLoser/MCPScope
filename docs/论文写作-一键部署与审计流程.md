# MCP 工具安全审计系统的原生命令行部署与运行

> 本文档可作为论文“系统设计与实现”章节的初稿。正式使用时，请根据论文结构调整章节编号，并用最终实验数据替换“初步验证”部分。

## 1. 设计目标

为降低 MCP 工具安全测试过程中的环境配置成本，并提高实验的可复现性，本文将公开索引查询、目标筛选、MCP 指纹探测、风险评估、测试计划生成、安全校验、受控执行和结果归档等模块封装为原生命令行审计系统。统一入口脚本负责检查 Python 与 Node.js 版本、创建隔离的 Python 虚拟环境并安装锁定依赖。使用者无需配置容器运行时即可启动完整审计流程。

系统总体流程如下：

```text
公开索引
   ↓
候选目标发现（不连接候选 MCP）
   ↓
授权范围确认
   ↓
MCP 服务指纹探测
   ↓
工具发现（initialize、tools/list）
   ↓
高风险候选筛选
   ↓
测试计划生成（规则模板或大模型）
   ↓
确定性安全校验
   ↓
人工授权确认
   ↓
单次 tools/call
   ↓
结果分类与证据保存
   ↓
人工复核
```

## 2. 原生命令行与依赖自举设计

系统要求 Python 3.11 及 Node.js 20 以上版本。Node.js 模块负责 MCP 协议连接、工具列表获取和工具调用，Python 模块负责公开索引查询、目标清单管理、风险规则匹配、测试计划生成、安全策略校验及结果分析。

统一入口脚本执行以下初始化操作：

- 检查 Python 和 Node.js 的最低版本；
- 在项目目录创建独立的 `.venv`；
- 按 `requirements.txt` 安装锁定的 Python 依赖；
- 按 `package-lock.json` 安装 MCP SDK 依赖；
- 将目标发现、指纹扫描和审计结果写入本地 `data/` 目录。

该方式减少了对特定容器平台的依赖，并通过虚拟环境和锁定文件维持依赖一致性。与容器隔离相比，原生运行对宿主机的隔离程度较低，因此系统仍限制默认行为，不自动执行 MCP 工具，并将主动目标探测与被动索引查询拆分为独立命令。

## 3. 自动化审计流程

系统提供目标发现、授权指纹扫描、单目标审计、受控执行和人工复核五类操作。

### 3.1 候选目标发现

`targets-discover` 查询 crt.sh、HuggingFace、GitHub 和 npm 等公开索引，提取可能部署 MCP 服务的候选地址。该阶段不连接候选 MCP 服务，并对 URL 进行规范化、去重和凭证清理。

### 3.2 授权指纹扫描

`targets-scan` 对经过人工筛选且处于授权范围内的候选地址执行 MCP 初始化和 `tools/list`。该命令必须提供明确的授权确认，并默认限制目标数量和并发数。

系统还提供离线报告与差异分析功能，用于比较两次指纹扫描中新增或消失的 MCP 服务、风险等级变化和工具集合变化。差异分析不发起新的网络请求。

### 3.3 工具发现

`discover` 阶段仅执行 MCP 初始化及 `tools/list`，用于获取工具名称、描述和输入参数模式，不调用实际工具。该阶段属于只读操作，其输出被原样保存，作为后续风险分析的输入和审计证据。

### 3.4 风险候选筛选

`audit` 阶段根据工具名称、工具描述和输入模式进行风险匹配。目前规则覆盖命令执行、文件操作、SQL、任意网络请求、凭证访问、权限变更、基础设施操作、资金交易和外部消息发送等风险类别。命中的工具按照风险等级排序并生成候选清单。

风险筛选的目标是缩小后续测试范围，而不是直接判定工具存在漏洞。一个工具具备高风险功能，仅表示该工具需要进一步验证，并不等同于存在可利用的安全缺陷。

### 3.5 测试计划生成

系统使用本地规则模板或大模型生成无害测试计划。默认计划只采用明显的合成标识符、保留测试域名、零金额、临时文件路径以及仅返回常量的 SQL。例如，对 SQL 执行工具生成如下测试语句：

```sql
SELECT 12345 AS audit_safe_probe;
```

该语句不引用数据表、视图、系统目录或业务数据，仅用于观察调用是否到达 SQL 执行边界。

### 3.6 受控执行

`execute` 阶段不会自动运行测试计划。只有计划通过确定性安全校验，并且操作者同时提供授权确认参数后，系统才允许执行一次 `tools/call`。系统还会检查是否已经存在调用结果，从而避免同一测试被重复执行。

### 3.7 人工复核

`review` 阶段由测试人员根据原始响应、规则分析结果和测试授权范围记录最终结论。系统允许记录“确认”“未确认”和“需要更多证据”等结果，但不会仅凭一次响应自动确认漏洞。

## 4. 大模型的作用与约束

大模型在本系统中不是漏洞判定主体，而是可选的测试计划生成器。其输入包括工具名称、工具描述、输入模式和风险类别，输出为结构化测试计划。

大模型输出不能直接进入执行阶段，而必须经过以下校验：

- 输出是否满足规定的 JSON 数据结构；
- 参数是否符合 MCP 工具的输入模式；
- 是否包含真实凭证或疑似敏感数据；
- URL 是否位于明确允许的测试资源范围内；
- SQL 是否仅查询字面常量；
- 命令是否仅输出固定审计标记；
- 文件路径是否位于专用临时目录；
- 高影响工具是否使用明显的虚假目标；
- 是否明确要求人工批准。

因此，系统采用“大模型生成、确定性规则约束、人工最终决策”的混合架构，避免将大模型输出直接作为可执行载荷或漏洞结论。

## 5. 安全控制

系统从执行权限、测试参数和证据完整性三个层面设置安全控制。

在执行权限方面，默认流程停止在人工审批之前。执行命令必须同时提供显式批准参数和授权确认文本。在测试参数方面，系统通过确定性校验器限制命令、SQL、文件路径、URL、收件人、金额及资源标识符。在证据完整性方面，系统分别保存测试计划、批准记录、原始响应、分析结果和人工结论，避免生成结果覆盖原始证据。

对于通过审批的测试计划，系统计算其 SHA-256 摘要并写入批准记录，以建立“测试计划—人工批准—执行结果”之间的对应关系，降低测试计划在批准后被替换的风险。

## 6. 证据管理

每次审计创建独立运行目录，主要文件如下表所示。

| 文件或目录 | 内容 |
| --- | --- |
| `manifest.json` | 审计目标、创建时间和流程状态 |
| `discovery.json` | MCP 工具发现原始结果 |
| `candidates.json` | 高风险候选清单及匹配证据 |
| `plans/` | 测试计划及确定性校验结果 |
| `approvals/` | 人工批准信息和计划哈希 |
| `raw/` | MCP 工具调用原始响应 |
| `results/` | 确定性规则分析结果 |
| `reviews/` | 人工复核结论 |

这种分层保存方式能够支持实验复查、问题定位和结果追溯。

## 7. 初步验证

在本地离线模拟环境中，测试服务器公开了两个 MCP 工具，其中 SQL 执行工具被识别为严重风险候选，普通文档搜索工具未被列入高风险候选。系统为 SQL 工具生成了仅返回字面常量的测试语句，确定性安全校验通过，并在实际调用前进入等待人工批准状态。

单元测试方面，风险识别与计划生成测试共 3 项，MCP 协议连接与调用测试共 12 项，均通过。初步测试说明系统能够完成工具发现、风险候选筛选、安全计划生成以及执行前拦截等核心流程。

> 注意：正式论文应补充不同操作系统上的首次依赖初始化时间、重复启动时间、目标发现耗时、指纹确认率和审计耗时。公开索引候选数量不能直接作为已确认 MCP 服务数量。

## 8. 系统定位与表述边界

本文系统应表述为“基于规则与大模型辅助的 MCP 高风险工具发现和受控安全验证系统”，不宜直接表述为“自动漏洞确认系统”。

高风险工具、测试调用到达业务层和漏洞确认是三个不同概念：

1. 高风险工具表示该工具具备可能产生安全影响的能力；
2. 测试调用到达业务层表示输入通过了部分接口校验；
3. 漏洞确认还需要结合授权模型、预期安全策略、实际影响和人工证据进行判断。

系统输出的自动分类主要用于辅助测试人员整理证据和确定复核优先级，最终漏洞结论仍由人工完成。

## 9. 后续实验指标建议

正式实验可以从以下指标评价系统：

| 评价维度 | 建议指标 |
| --- | --- |
| 部署能力 | 首次初始化成功率、依赖安装时间、重复启动时间 |
| 工具发现 | 工具发现完整率、协议连接成功率、平均发现时间 |
| 风险筛选 | 准确率、召回率、误报率、漏报率 |
| 计划生成 | Schema 合规率、安全校验通过率、大模型输出失败率 |
| 安全控制 | 危险测试载荷拦截率、未授权执行拦截率、重复调用拦截率 |
| 运行效率 | 单目标平均审计时间、单工具计划生成时间 |
| 结果复核 | 自动分类与人工结论的一致率 |

实验数据应区分离线模拟 MCP、受控测试环境和真实授权目标，避免将不同环境下的结果直接合并比较。
